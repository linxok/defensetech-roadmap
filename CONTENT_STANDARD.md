# Стандарт контенту курсу

Цей документ — джерело правди для всіх, хто редагує модулі курсу.
Він фіксує, як виглядає якісний модуль, що вважається завершеним і як
перевіряється якість. Правила застосовуються і до профільних модулів
треку **Drone / Autopilot Software** (05–09), і до оглядових.

## 1. Статуси модулів

Кожен модуль має рівно один статус, зафіксований у його `README.md`
рядком `> Статус: <статус>` та в таблиці `README.md` курсу.

| Статус | Що це означає | Мінімальні вимоги |
|---|---|---|
| `stub` | Каркас: є мета й теми, контенту немає | README з метою та переліком тем |
| `outline` | Огляд: можна зрозуміти місце теми й почати працювати з первинними джерелами | README з 5+ джерелами та 3+ контрольними питаннями; lab з очікуваним результатом; checklist з бінарними критеріями |
| `complete` | Самодостатній модуль: лабораторну можна виконати за README без зовнішніх туторіалів | Усе з `outline` + `checks/` і `solution/` для лабораторної + ≥5 контрольних питань з перевіркою + розібрані типові помилки з конкретними повідомленнями |

Підвищувати статус можна лише за виконання всіх вимог рівня.
Знижувати — обов'язково, якщо вимоги перестали виконуватись.

## 2. Структура модуля

```text
NN-topic/
├── README.md              # мета, теорія-мінімум, контрольні питання, зв'язок з capstone
├── detailed-guide.md      # маршрут саме цього модуля (посилається на docs/learning-workflow.md)
├── lab.md                 # покрокова лабораторна + очікуваний результат + перевірка
├── checks/                # автоматична перевірка лабораторної (pytest/CLI, exit code)
├── solution/              # еталонне рішення лабораторної
├── practice.md            # самостійне завдання без підказок + типові збої
├── homework.md            # завдання на тиждень з критеріями приймання
├── mini-project.md        # специфікація компонента портфоліо + Definition of Done
├── project-ideas.md       # 3 конкретні ідеї зі стеком і результатом
├── real-world-scenario.md # робочий сценарій і обмеження
├── checklist.md           # бінарні критерії завершення (з посиланнями на checks/)
├── self-assessment.md     # питання для самоперевірки без підказок
├── interview-questions.md # 3 питання рівня співбесіди з ключем відповіді
├── faq.md                 # 3 модульні питання, які реально виникають
├── cheat-sheet.md         # команди, параметри, ID повідомлень — коротко
├── resources.md           # первинні джерела (головний список)
├── templates.md           # які шаблони з docs/templates.md потрібні саме тут
└── examples/              # запускні приклади
```

`further-reading.md` більше не створюється: додаткові джерела йдуть у
`resources.md` з поміткою `[додатково]`.

## 3. README модуля

Обов'язкові елементи:

1. Рядок статусу: `> Статус: outline`. Після нього — мета модуля 2–4 реченнями.
2. **Мінімум теорії своїми словами** — не переказ документації, а мапа:
   що це, навіщо, як пов'язано з сусідніми модулями. Кожне твердження
   має бути конкретним (версії, стандарти, числа, імена протоколів).
3. **5–10 контрольних питань**, на які відповідь перевіряється кодом,
   логом або `checks/`, а не «відчуттям».
4. **5+ первинних джерел** з посиланнями (специфікації, офіційні docs,
   RFC, вихідний код) — саме первинних, не переказів.
5. **Очікуваний результат**: що учень матиме після модуля (артефакт).
6. **Зв'язок з capstone**: конкретний крок `capstone/README.md`.
7. **Типові помилки** — тільки специфічні для теми, з текстом помилки
   або симптомом (не загальні «неправильні залежності»).

Орієнтир обсягу для `complete`: 80–150 рядків унікального тексту.
Водночас обсяг не є метою: краще 80 конкретних рядків, ніж 150 загальних.

## 4. Лабораторна робота

`lab.md` містить:

- **Мета** — одне речення.
- **Передумови** — версії ПЗ та команди встановлення.
- **Кроки** — кожен крок можна виконати й перевірити окремо.
- **Очікуваний результат** — конкретні значення, файли, вивід.
- **Перевірка** — команда, яка це доводить:
  `python checks/check_lab.py --target solution` (або pytest).
- **Розбір збоїв** — 2–3 конкретні помилки та їх причини.

Правила для `checks/`:

- Скрипт завершується `exit 0` лише коли завдання справді виконане.
- На порожньому/шаблонному рішенні (`stub`) скрипт падає.
- Перевіряється результат, а не факт наявності файлу.
- Офлайн-перевірка: без SITL, Docker і мережі (використовуйте
  записані фікстури MAVLink-повідомлень).
- `solution/` — робоче еталонне рішення, з яким `checks/` проходить.

## 5. Проєкти та мініпроєкти

Definition of Done компонента — бінарний чекліст:

- [ ] Команда запуску з чистого середовища працює (`docker compose up` або README-команда).
- [ ] Є тест, який падає на поламаному вході (не лише happy path).
- [ ] Заміряно хоча б одну метрику (латентність, throughput, розмір логу).
- [ ] README містить приклад виводу/скріншот.
- [ ] Код проходить лінтер/компіляцію в CI.

## 6. Якість коду прикладів

- Приклади або запускаються, або мають у шапці коментар з точним
  способом запуску. Немає «псевдокоду, який ніхто не перевірив».
- Заборонено створювати з'єднання (RabbitMQ, БД, HTTP) на етапі імпорту.
- У async-коді заборонені блокуючі виклики без `asyncio.to_thread`
  або async-драйвера; `asyncio.wait` приймає лише задачі.
- Кожен мережевий виклик має таймаут і обробку помилки.
- Версії залежностей пінуються у `requirements.txt`.

## 7. Заборона дублювання

Той самий текстовий блок не можна повторювати у двох модулях.
Спільні матеріали живуть один раз:

- загальний порядок навчання — `docs/learning-workflow.md`;
- курс-рівневі питання — `docs/faq.md`;
- шаблони коду — `docs/templates.md`;
- усе інше — сторінка-посилання в модулі.

Перевірка перед комітом:

```bash
python3 scripts/check_duplicates.py
```

Скрипт падає, якщо знаходить однаковий блок (≥ 120 символів) у двох
різних модулях. Виняток — цитати стандартів і повідомлення компіляторів,
але й вони мають бути оформлені з посиланням на джерело.

## 8. Markdown і збірка

- Лінт: `npx markdownlint-cli2 "**/*.md" "!venv/**" "!.kilo/**"`.
  Конфіг — `.markdownlint-cli2.jsonc`.
- Сайт: `mkdocs build --strict` має проходити без попереджень.
- Заголовки унікальні в межах файлу; списки й код-блоки — з порожніми
  рядками навколо; у код-блоків завжди вказана мова.

## 9. Мова

- Назви, README курсу, навігація — англійською.
- Контент модулів, лабораторні, коментарі до коду — українською.
- Ідентифікатори коду, команди, назви протоколів — англійською завжди.
