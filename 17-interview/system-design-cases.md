# System design кейси для флоту дронів

Три кейси з рамками відповіді. Мета — навчитися міркувати вголос:
вимоги → оцінки → схема → вузькі місця → відмови.

## Кейс 1: телеметрія 1000 дронів у реальному часі

**Вимоги.** 1000 дронів, 5 кадрів/с кожен (≈5 000 msg/s), затримка
до UI < 2 с, зберігання 30 днів, доступність 99.9%.

**Оцінки.** Кадр ≈300 байт → ≈1.5 МБ/с у сирому вигляді, ≈4 ТБ на
30 днів із запасом. Кожен дрон — 5 записів/с → 5 000 INSERT/s.

**Схема.** Регіональні шлюзи (stateless) → Redis Streams або Kafka з
партиціями за `drone_id` → воркери батчами пишуть у TimescaleDB
(гіпертаблиця + retention) → WS-шар читає останній стан із Redis і
транслює підписникам. Pub/sub між WS-інстансами для масштабування.

**Вузькі місця.** Кількість WS-з’єднань; запис у БД (батчинг/COPY);
дедуплікація при повторній доставці; гарячі партиції.

**Відмови.** Брокер недоступний — шлюз буферизує локально з обмеженим
розміром; БД повільна — черга росте, алерт на lag; UI показує
`last seen` замість нулів.

## Кейс 2: командний канал керування дроном

**Вимоги.** Команда ARM/takeoff/RTL доходить із підтвердженням,
затримка < 500 мс, без дублювання дій, аудит усіх команд.

**Схема.** Оператор → API команд → черга команд (пріоритетна) →
gateway із MAVLink-з’єднанням → `COMMAND_LONG` → `COMMAND_ACK` →
подія в аудит-лог і WS-оновлення UI.

**Ключові рішення.** Ідемпотентний `command_id`; таймаут ACK і
максимум 3 спроби; блокування небезпечних команд без підтвердження
оператора; окремий канал для команд (не змішувати з телеметрією).

**Відмови.** Втрата лінку — команда не підтверджена, UI показує
невдачу, жодного «успіху за замовчуванням»; повторне підключення
дрона — стан синхронізується з heartbeat.

## Кейс 3: зберігання і розбір польотних логів

**Вимоги.** 200 МБ логів на політ, 50 польотів/день, зберігання рік,
аналіз топіків за запитом < 30 с.

**Схема.** Завантаження об’єктами (S3-сумісне сховище) → метадані в
PostgreSQL → черга на обробку → аналізатор витягує метрики
(max attitude, saturation, voltage sag) → звіт у сховищі + індекс.

**Ключові рішення.** Не зберігати логи в БД; вибіркове читання
топіків (pyulog), а не повне завантаження; кеш метрик; retention
політика для сирих файлів.

**Відмови.** Битий файл — задача падає в DLQ, метадані позначаються
`failed`; черга переповнена — обмеження на паралельну обробку й
пріоритет свіжих польотів.

## Як тренувати

1. Візьміть кейс, за 10 хвилин напишіть вимоги й оцінки в числах.
2. Намалюйте схему і назвіть по два вузькі місця та відмови.
3. Порівняйте з рамкою вище — не шукайте ідентичності, шукайте
   пропущені категорії.
4. Повторіть кейс через тиждень за 5 хвилин.
