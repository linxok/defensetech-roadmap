# 08. PX4: параметри, uORB і логи

> Статус: complete

Розібрати PX4 зсередини настільки, щоб упевнено читати його параметри, топіки uORB і польотні логи ULog. Модуль дає два практичні інструменти: CLI-менеджер параметрів через MAVSDK і офлайн-звіт по логу через pyulog. Разом це база післяполітної діагностики: без неї неможливо довести, що автопілот працював штатно, а не «якось долетів».

## Що потрібно зрозуміти

- PX4 збирається в один бінарник, але всередині складається з модулів (`commander`, `navigator`, `ekf2`, `mc_att_control`, `mc_pos_control`, `logger`), які не викликають один одного напряму.
- uORB — внутрішня pub/sub-шина: модуль публікує топік фіксованого формату, інші модулі його читають. Типові топіки: `vehicle_attitude`, `vehicle_local_position`, `vehicle_status`, `battery_status`, `actuator_outputs`. Дивитися їх у shell PX4: `listener vehicle_attitude`, `uorb top`.
- Параметри: імʼя до 16 символів `A-Z0-9_`, перший символ — літера (`MPC_XY_VEL_MAX`), тип `int32` або `float`, значення переживає перезапуск. У shell: `param show MPC_*`, `param set MPC_XY_VEL_MAX 12.5`, `param save`, скидання — `param reset`.
- MAVSDK: `System().connect('udp://:14540')`, далі `drone.param.get_param_float`, `set_param_float`, `get_all_params`. Порт `14540` — API-канал PX4 для MAVSDK, `14550` — телеметрія для наземної станції.
- ULog самодостатній: заголовок `ULog` із версією, секція definitions із форматами топіків, параметрами й метаданими, далі семпли. Кожен запис має `timestamp` у мікросекундах від старту, монотонний у межах одного `msg_id`.
- `pyulog` читає ULog без PX4: `ULog(path).data_list` дає обʼєкти з `.name`, `.data` (словник «поле → масив») і `.msg_info`; `ulog.get_dataset('vehicle_attitude')` бере один топік. У CLI є `ulog_info`, `ulog_messages`, `ulog_params`, `ulog2csv`.
- Порядок розбору логу: таймлайн режимів і подій → розбіжність `vehicle_attitude` із сетпойнтом → насичення `actuator_outputs` → просідання напруги в `battery_status` → текстові події з `ulog_messages`.
- Топіки пишуться з різною частотою, тому зіставляти події можна лише за `timestamp`, а не за порядковим індексом семпла.
- SITL: `make px4_sitl gz_x500` (Gazebo). jMAVSim із v1.15 знято з офіційного toolchain, тому `make px4_sitl jmavsim` на нових версіях падає з `No rule to make target 'jmavsim'`.
- `param set` змінює значення в RAM і зберігає його у файл параметрів, але частина параметрів набуває чинності лише після перезавантаження. Тому після запису завжди читайте значення назад, а за потреби перезавантажуйте й перевіряйте `ulog_params` у наступному лозі.
- У лозі параметри лежать у `P`-записах секції definitions; якщо параметр змінювався в польоті, в data-секції зʼявиться додатковий `P`-запис із новим значенням — це дає відновити конфігурацію на момент події.
- Logger — окремий модуль PX4: якщо його вимкнено або відсутня SD-карта, після польоту не буде що аналізувати. Це перше, що перевіряють, коли «лог порожній».
- Відсутність запису не означає відсутності події: модуль, який упав, міг не встигнути опублікувати топік, тому `ulog_messages` і `vehicle_status` переглядають першими.

- MAVSDK сам формує MAVLink-кадри, тож для параметрів не треба знати поля повідомлень; але `get_all_params` — повільна операція, їй не місце в циклі керування.
- Shell PX4 (`pxh>`) доступний у SITL і по MAVLink-shell на залізі: `param`, `listener`, `uorb top`, `logger` — базовий набір для швидкої перевірки гіпотез.
- Одиниці й порядок полів беріть із `uORB Message Reference`: `vehicle_attitude.q` — кватерніон `[w, x, y, z]`, `vehicle_local_position` — NED у метрах; вгадувати формат небезпечно.
- Часові мітки PX4 — час від старту, не UTC: для зіставлення із зовнішніми подіями потрібен `time_ref_utc` з метаданих логу.

## Анатомія розбору логу

1. Метадані (`ulog_info`): версія прошивки, тривалість, модель — щоб не інтерпретувати лог чужої збірки.
2. Параметри на старті й зміни в польоті (`ulog_params`).
3. Текстові події (`ulog_messages`): arming, failsafe, попередження.
4. Топіки керування: сетпойнт проти фактичного значення за одним і тим самим `timestamp`.
5. Виконавчі органи й живлення: насичення `actuator_outputs`, просадка `battery_status`.
6. Гіпотеза → перевірка ще одним датасетом, а не висновок «на око» з одного графіка.
7. Перевірити повноту логу: `ulog_info` показує тривалість і дропаути; обірваний лог не можна трактувати як «подій не було».
8. Записати висновок у звіт із посиланням на конкретні датасети й діапазони `timestamp`.

## Контрольні питання

1. Якою підкомандою знайти параметри за префіксом, не знаючи повного імені, і як виглядає вивід `list MPC_XY`?
2. Що станеться при `set mpc_xy_p 1.0` і чому валідація імені завершується `SystemExit`, а не `ValueError`?
3. Які топіки ULog потрібні, щоб пояснити різкий крен, і в яких одиницях їхні поля?
4. Як `uorb top` доводить, що модулі спілкуються саме через uORB, а не прямими викликами?
5. Як переконатися, що записане значення параметра застосувалося? Назвіть два незалежні підтвердження.
6. Чому `--help` має завершуватися кодом 0 і що ламає цю вимогу?
7. Яка команда SITL замінила jMAVSim у PX4 ≥1.15?
8. Чому аналіз логу будують на `timestamp`, а не на порядковому індексі запису?
9. Де в ULog зберігаються параметри й текстові повідомлення і якими утилітами pyulog їх витягти?
10. Що зʼявиться в лозі, якщо параметр змінили в польоті?

## Зв'язок з capstone

`capstone/README.md` → «Метрики для портфоліо» вимагає заміряти «розмір запису в PostgreSQL за годину польоту» та наскрізні метрики; ULog-аналіз додає те, чого не видно з телеметрії (просадка напруги, насичення виходів, спрацювання failsafe). «Що далі» п. 1 — перехід від SITL до реального FC: ті самі `param`/ULog-інструменти працюють і на залізі.

## Як перевіряється

- `python checks/check_lab.py --target <тека>` імпортує `px4_param.py` без SITL, Docker і мережі.
- `validate_name` перевіряється на `MPC_XY_VEL_MAX` і чотирьох невалідних іменах — кожне мусить кинути `SystemExit`.
- `format_param('MPC_XY_P', 0.85)` мусить зберегти і імʼя, і значення.
- `format_params` мусить відсортувати вхід і дати `['A_PARAM = 1', 'B_PARAM = 2']`.
- `parse_args(['get', 'MPC_XY_P'])` має дати `command == 'get'` і `name == 'MPC_XY_P'`.
- `python px4_param.py --help` має завершитися з кодом 0 — це ловить `asyncio.run` на рівні модуля.
- Той самий скрипт після `--target solution` запускається на вашій теці: контракт не залежить від SITL і не потребує PX4.

## Типові помилки

- `SystemExit: invalid PX4 parameter name: 'mpc_xy'` — імʼя в нижньому регістрі або з дефісом не проходить `^[A-Z][A-Z0-9_]{0,15}$`.
- `--help` зависає або завершується кодом ≠ 0 — `asyncio.run(main())` викликано на рівні модуля; перенесіть під `if __name__ == '__main__':`.
- `make px4_sitl jmavsim` → `No rule to make target 'jmavsim'` — jMAVSim знято з офіційного toolchain у v1.15, запускайте `make px4_sitl gz_x500`.
- `MemoryError` на багатодесятимегабайтному лозі — ULog читається цілком замість вибіркових датасетів через `get_dataset`.
- Запис у параметр типу `int32` через `set_param_float` дає помилку типу MAVSDK; тип беріть із `get_all_params` і для int використовуйте `set_param_int`.
- `TimeoutError: no PX4 connection at udp://:14540` — SITL не стартував або MAVSDK вказує на чужий порт.
- Порівняння подій «за індексом» дає хибні висновки: топіки мають різну частоту, зіставляти їх можна лише за `timestamp`.
- `KeyError: 'vehicle_attitude'` від `get_dataset`, якщо топік не логувався: спершу дивіться список `.data_list`.
- Після `set` значення виглядає старим — параметр застосовується лише після reboot; читайте назад і перезавантажуйте, якщо це передбачено параметром.
- `print(param)` дає `Param(name='...', value=...)` замість рядка — форматуйте через `format_param`, не покладайтеся на `repr`.
