# 08. PX4: параметри, uORB і логи

> Статус: complete

Навчитися працювати з PX4 через MAVSDK: параметри, стани, а також розбирати ULog — ключова навичка діагностики польотів.

## Що потрібно зрозуміти

- PX4 — модульна архітектура з uORB pub/sub усередині; модулі спілкуються повідомленнями, а не прямими викликами.
- Параметри PX4: імена до 16 символів (`MPC_XY_VEL_MAX`), тип і значення зберігаються між стартами.
- MAVSDK `System().param` дає `get_param_float`, `set_param_float`, `get_all_params`; зміни застосовуються миттєво, якщо параметр не вимагає reboot.
- ULog — формат логів PX4: топіки, семпли, метадані; `pyulog` читає їх без PX4 (`ULog(path).data_list`).
- Ключові топіки для аналізу: `vehicle_attitude`, `vehicle_local_position`, `battery_status`, `actuator_outputs`, `vehicle_status`.
- Порядок розбору логу: таймлайн режимів → відхилення attitude → насичення виходів → просідання напруги → події (failsafe/arming).
- SITL PX4 піднімається `make px4_sitl gz_x500`; MAVSDK підключається до `udp://:14540`.

## Контрольні питання

1. Як знайти параметр за призначенням, не знаючи імені?
2. Що станеться при спробі set_param із невалідним іменем?
3. Які топіки ULog потрібні, щоб пояснити, чому дрон смикнувся?
4. Чим PX4-архітектура принципово відрізняється від «прошивка-моноліт»?
5. Як перевірити, що зміна параметра застосувалася, а не «загубилася»?

## Очікуваний результат

CLI-менеджер параметрів PX4 із валідацією і форматуванням (`solution/px4_param.py`) та звіт по ULog.

## Типові помилки

- Писати параметр без читання назад: частина параметрів вимагає reboot.
- Передавати ім’я параметра в нижньому регістрі — PX4 імена uppercase.
- Читати ULog цілком у пам’ять для 200-МБ логу замість вибіркових топіків.
- Ігнорувати `timestamp` у топіках: без синхронізації події не зіставити.
