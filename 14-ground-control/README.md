# 14. Наземна станція (GCS)

> Статус: outline

Побудувати веб-GCS: мапа, телеметрія в реальному часі, тривоги — з фокусом на надійність UX для оператора.

## Що потрібно зрозуміти

- Оператор приймає рішення за секунди: ціна помилки UI — втрачений дрон, тому стан має бути однозначним (armed/disarmed, link/ no-link).
- WebSocket для телеметрії, HTTP для команд; команди завжди з підтвердженням і таймаутом.
- Leaflet/MapLibre + тайли: для офлайну — локальний тайл-сервер або кеш, бо в полі інтернету може не бути.
- Траєкторія: обмеження кількості точок (ring buffer) і проста геометрія; малювання тисяч точок у DOM вбиває FPS.
- Стан: валідація кадрів перед setState, інакше NaN ламає мапу.
- Тривоги: пороги battery/link/vibration з пріоритетами; оператор не має шукати проблему в цифрах.
- Тестування UI: чисті функції (форматування, валідація, трейл) тестуються Node без браузера — це і є `checks/`.

## Контрольні питання

1. Як відрізнити «немає даних» від «дані нульові»?
2. Скільки точок траєкторії тримати в пам’яті?
3. Як працювати без інтернету і тайлів?
4. Які команди потребують подвійного підтвердження?
5. Як тестувати компонент без браузера?

## Очікуваний результат

GCS-компонент із тестованою логікою (`solution/telemetry-format.mjs`, `solution/gcs-page.tsx`).

## Зв'язок з capstone

## Типові помилки

- Малювати полілінію без обмеження точок — браузер зависає
- Показувати 0 замість «—» при відсутності даних
- NaN у координатах валить карту
- Команда ARM без підтвердження і без перевірки стану
