# Як проходити модулі

Це спільний робочий цикл для всіх модулів курсу. Модульні
`detailed-guide.md` лише уточнюють, у якому порядку проходити файли
саме цього модуля, і посилаються сюди.

## Робочий цикл модуля (7 етапів)

### 1. Теорія з питаннями (20% часу)

Прочитайте README модуля та первинні джерела з `resources.md`.
Не «продивляйтесь» документацію: після кожного джерела випишіть
2–3 питання, на які джерело не відповіло, і знайдіть відповідь у
специфікації або вихідному коді. Конспект — стисло, своїми словами.

Критерій: можете за 5 хвилин намалювати схему теми на білому аркуші
без підглядання.

### 2. Приклади

Запустіть кожен приклад з `examples/`. Перед запуском передбачте
вивід. Якщо вивід відрізняється — це і є тема для розбору.
Приклади, що вимагають SITL/Docker, позначені в `examples/README.md`.

### 3. Лабораторна

Виконуйте `lab.md` кроками, не копіюючи код бездумно. Після кожного
кроку — перевірка з розділу «Перевірка». Якщо застрягли більш ніж на
30 хвилин: порівняйте з `solution/`, але поверніться і відтворіть
крок самостійно. Записуйте помилки та їх причини — це ваша база для
`faq.md` і майбутніх співбесід.

### 4. Практика без підказок

`practice.md` — повторення завдання у зміненому контексті. Тут
заборонено дивитись у `solution/`, доки не отримаєте робочий
результат. Мета — перевірити, що знання переносяться, а не
запам'ятались як послідовність команд.

### 5. Мініпроєкт

Оберіть компонент з `mini-project.md` або `project-ideas.md` і
реалізуйте його в окремому репозиторії. Definition of Done — у
`CONTENT_STANDARD.md`, розділ 5. Для профільних модулів (05–09)
найкращий мініпроєкт — наступний крок `capstone/`.

### 6. Самоперевірка

Пройдіть `checklist.md`: кожен пункт — команда або артефакт, а не
відчуття. Запустіть `checks/` проти власного рішення. Дайте відповіді
на `self-assessment.md` вголос, без нотаток.

### 7. Публікація

Закомітьте результат, напишіть короткий README (проблема → рішення →
запуск → метрики), опублікуйте пост або нотатку. Один публічний
артефакт на тиждень — мінімум для портфоліо.

## Тижневий ритм

| Активність | Частка часу | Перевірка |
|---|---|---|
| Первинні джерела | 20% | питання до себе, схема |
| Практика в capstone | 60% | тест/лог/метрика |
| Верифікація й публікація | 20% | commit/пост/README |

Раз на два тижні — контрольний прогон «з нуля за 30 хвилин»: підняти
середовище й отримати робочий результат останнього компонента без
підказок.

## Типові проблеми (спільні)

- **Залежності не сумісні.** Перевіряйте версії з `requirements.txt`;
  для SITL — версію ArduPilot з `docs/setup.md`.
- **Порт зайнятий.** `ss -lunp | grep 14550` показує, хто тримає
  MAVLink-порт; SITL, MAVProxy і gateway не ділять один порт.
- **Неправильні адреси.** UDP `127.0.0.1:14550` — це GCS-порт SITL,
  а не порт, куди SITL слухає; для другого клієнта беріть 14551+.
- **Права доступу.** Serial-порти потребують групи `dialout`;
  перевірка: `ls -l /dev/ttyUSB0`.
- **Блокуючий виклик в async.** Симптом: цикл «завмирає» на секунди.
  Рішення — `asyncio.to_thread` або async-драйвер.
- **Тихі винятки.** `except Exception: pass` ховає причину; логуйте
  тип і текст помилки, а потім уже ковтайте.

## Де шукати відповіді

1. Первинне джерело: специфікація, вихідний код, changelog.
2. `docs/tools.md` — інструменти діагностики.
3. `docs/glossary.md` — терміни.
4. Пошук у репозиторії: `grep -rn "TERM" --include='*.py'`.
5. Спільноти: ArduPilot Discuss, PX4 Slack, ROS Discourse,
   MAVLink GitHub Discussions.

## Що робити після модуля

Поверніться до `capstone/README.md`, знайдіть крок, що відповідає
модулю, і перевірте, що компонент capstone досі запускається.
Модуль вважається засвоєним, коли capstone став функціональнішим,
а не коли прочитано README.
